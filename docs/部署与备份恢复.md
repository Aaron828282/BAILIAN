# 部署与备份恢复

## 部署方式选择

| 方式 | 适用 | 门槛 |
| --- | --- | --- |
| Node 24 直接启动 | 本机试用、已有进程管理和 HTTPS 的服务器 | Node 24，配置环境变量或 .env |
| Docker Compose + Caddy | 独立 Linux 服务器 | Docker / Compose、域名、80 与 443 端口 |

入口命令见 README。公网服务必须配置 HTTPS PUBLIC_URL；HTTP 只允许 localhost / 回环地址。后台写入严格检查 Origin 与 CSRF，反向代理应保留浏览器 Origin。不能将工作台挂到子路径。

## 必须保管的配置与数据

- `.env`：VAULT_KEY 是数据库加密主密钥，丢失后无法恢复已存 Key、包备份及缓存结果。RELAY_TOKEN 是兼容旧版的不计费共享令牌；ADMIN_PASSWORD 只在第一次创建数据库时初始化账号。
- `resources/client-material.json`：兼容现有 Key 包所需的客户验签公钥与拆分解密材料。部署包按功能需要携带此材料，不含经营者签名私钥。持有此文件的人具备解开对应包的能力，请将完整部署包仅交给可信服务器经营者。
- 数据库：Node 模式默认 `data/relay.sqlite`；Docker 模式在 `bailian-relay_relay_data` 卷，容器内 `/app/data/relay.sqlite`。如使用不同 Compose 项目名，卷名前缀随之改变。

初始密码见管理员登录.txt，建议转存至密码管理器。登录后改密码会使现有会话失效，随后 .env 中的旧 ADMIN_PASSWORD 不会覆盖数据库新密码。旧共享令牌轮换需要更新 .env 的 RELAY_TOKEN 并重建服务。新中转 Key 在后台创建、复制和停用，相关状态持久化到数据库。VAULT_KEY 不可直接换新。

## 在线一致性备份

使用 SQLite 原生 backup API 生成一致性快照，不直接复制正在写入的 sqlite 单文件。

Node 模式：

```sh
node --env-file=.env scripts/backup.cjs
```

Docker 模式：

```sh
docker compose exec relay node scripts/backup.cjs
```

脚本输出本次快照的完整路径，备份位于 data/backups。然后按输出的准确文件名取出：

```sh
docker compose cp relay:/app/data/backups/本次准确文件名.sqlite ./本次准确文件名.sqlite
```

同时离线保管原 .env 与解包材料；数据库快照本身不能代替加密主密钥。备份包含账号池、累计用量、预占、包原件、响应缓存、中转 Key、余额、价格、计费流水和审计记录。快照文件属于敏感资产，保存到受限目录。

## 恢复到新目录或新服务器

先停止原实例，防止两份独立数据库同时分配同一批 Key 的额度。保留原目录和数据卷作为回退依据，不执行 docker compose down -v。

Node 模式：新建独立恢复目录，放入同版本程序和原 .env，创建空 data 目录，将快照复制为 data/relay.sqlite。等待旧实例租约最多 60 秒过期后启动。检查上游与中转 Key 数量、累计用量、余额、单价和待核对请求。

Docker 模式：将同版本程序与原 .env 放入新目录，使用新的 Compose 项目名创建空卷，再导入快照：

```sh
docker compose -p bailian-recovered build relay
docker compose -p bailian-recovered create relay
docker compose -p bailian-recovered cp ./本次准确文件名.sqlite relay:/app/data/relay.sqlite
docker compose -p bailian-recovered run --rm --no-deps --user root --entrypoint chown relay node:node /app/data/relay.sqlite
docker compose -p bailian-recovered --profile https up -d
```

仅对新创建、尚无业务写入的恢复卷执行上述复制。数据文件保持 node 用户可读写。若提示 INSTANCE_ACTIVE，确认旧实例已停止，等待原租约到期再启动。

恢复快照会回到备份时点；备份后的真实消费需要在正式恢复分配前核对。发送中请求在重启后进入待核对，已登记任务 ID 的视频继续查询。结果不明不会自动退额度或重发。

## 运行约束与核对流程

单实例运行，不要使用 PM2 cluster、多个副本或跨主机共享同一个 SQLite 文件。服务使用 60 秒数据库租约，每 10 秒续租。每个上游阿里 Key 最多两个未结算请求。请求体同时保留的总字节量限制为 80MB；单 JSON 45MB（文本 1MB），控制内存峰值。

管理员在阿里控制台确认实际结果，再到“请求与核对”填写用量和依据：明确零消耗填 0；已成功填实际 Token、张数或秒数。计费文本还需填写输入与输出 Token 明细，其和必须等于总用量。核对会按原单价同时结算本地用量及中转余额，不会撤回上游任务。

上游明确拒绝后 Key 冷却 60 秒；可修复权限或余额后重新启用。系统不会反复重发生成。Key 总量上限 10000，请求记录 100000 条；达到请求上限时停止接收新生成，保留所有用量和幂等记录。应在接近上限时规划保留策略升级，不能直接清库来绕过预算。

数据库会增长，因为保留幂等响应和包备份。监测磁盘使用量、待核对请求、错误日志和 /healthz；管理员密码、Key 正文、原始请求提示词不会主动写入服务日志。缓存是加密保存的返回结果，不是作品库。

## 从 1.0.0 升级到 1.1.0

先生成在线一致性快照，停止旧实例，将 1.1.0 程序放入新目录并保留原 .env、解包材料与完整数据库，再按原部署方式启动。Docker 可在保留原数据卷的情况下重新构建应用镜像。应用启动时自动添加计费表和请求归属字段；历史请求归入旧共享令牌并保留原有幂等和用量。价格初始为空，不会自动套用示例单价或追收历史消费。

升级后检查原号池、备份包、累计用量和待核对请求，再配置售价、创建新中转 Key。旧令牌仍不计费，可在调用方切换后停用；服务重启不会重新启用被停用的旧令牌。回退旧程序必须使用升级前快照，不能直接拿新结构数据库运行旧版本；正式消费后的回退需要先对账，避免丢失新账单。

## 归档备忘

本地预算与阿里账户结算分开，备份必须包含原主密钥。部署交付不意味着真实账号的地区、模型权限和余额已核验；上线时先用受控的小额度 Key 验证实际环境。
